# Publication reliability (A06/A08)

The consistency boundary is the current run's pipeline JSON snapshots, summaries, dated digest, navigation homepage, HTML archive, seen-paper JSON and completion manifest. Retrieval caches and downloaded PDFs remain independently reusable inputs outside this boundary. Scientific selection, clustering, prompts and generation algorithms are unchanged.

## Writes, staging and recovery

`digest_core.atomic.atomic_write_text()` writes UTF-8 bytes to a named temporary file in the destination directory, flushes, fsyncs and closes it, then uses `os.replace()`. The destination is never truncated first. `save_json()` retains its signature and JSON formatting and now uses this mechanism. Standalone HTML persistence helpers use it too.

`ResearchDigestPipeline` holds generated JSON in memory until a digest is ready. `DigestPublisher.publish()` renders the post, navigation and archive including the proposed new post before modifying published destinations. It adds summaries and the caller's staged state, then stages every output beside its destination. Staged bytes must match generated bytes; JSON must parse and HTML must contain its document/body boundaries. Navigation/archive must reference the proposed post. These are structural completeness checks, not browser rendering or scientific-quality validation. Failure-placeholder summaries (`generation_mode=unavailable`) cannot be published; supported extractive summaries can.

`replace_files()` creates backups of existing targets before the first replacement. Individual replacements are atomic, but **the entire set is not a filesystem transaction**. On a caught replacement exception it restores replaced originals in reverse order and removes newly created targets. Successful commits and successful rollbacks clean up temporary/backup files. Historical posts are not rewritten unless the current run deliberately replaces the same dated filename, matching prior behavior.

A cooperating pipeline or standalone publisher holds `docs/.publication.lock` (relative to the configured homepage directory). Exclusive creation prevents concurrent writers from this application. Calls within one pipeline share the lock. A normal return or recoverable exception removes it. A failed rollback raises `PublicationRollbackError`, retains available `.backup` files and leaves the lock in place. A crash/forced termination can also leave the lock and staged/backed-up files. Subsequent runs fail closed rather than guessing recovery state.

**Recovery after a stale lock or failed rollback is manual:** first confirm no process still owns the run; preserve the remaining backups and diagnostics; inspect the manifest and affected files; restore a consistent prior set (or complete and independently validate a replacement); only then remove the stale lock. Do not delete backup files merely to unblock a retry. No automatic crash-recovery journal is claimed.

The guarantees assume normal local-filesystem atomic rename semantics. A reader ignoring the manifest/lock can observe mixed versions during the short replacement interval. Power-loss durability across a group, parent-directory fsync, noncooperating writers and distributed filesystems are not covered. Backups and a fail-closed lock improve recovery but cannot guarantee it after hardware/storage failures.

## Completion manifest and deployment gate

`docs/publication.json` is replaced last. It contains `status=published`, a `run_id`, UTC creation time, retrieval/runtime metadata, summary generation-mode counts, and relative paths/roles/SHA-256 hashes for all artifacts in the consistency boundary. The manifest does not hash itself. No schema changes are made to the existing paper arrays, HTML pages or URL-to-boolean archive.

Run `python src/digest_core/publication.py --run-id <expected-id>` to verify a publication. The validator rejects an existing publication lock, a stale run ID, missing required post/index/archive/summaries roles, missing or changed artifact bytes and invalid JSON/HTML. A prior manifest therefore cannot pass as the current CI refresh. This manifest is a completeness marker, not an atomicity mechanism or scientific-verification assertion.

The pipeline uses `DIGEST_RUN_ID` when set, otherwise a new UUID. `PipelineRunResult` adds `status` (`published`, `no_publication`, `failed`, with `unknown` as a compatibility default) and `run_id`. Existing counts, `weekly_post` and retrieval diagnostics remain intact. Publication exceptions propagate to callers; no successful result is returned after incomplete publication.

## Seen-paper state

Selection no longer invokes `mark_papers_seen()`. Before publication, `archive_with_seen()` prepares a merged URL-to-boolean history without writing it. Only URLs actually included in featured summaries or brief references are added; excluded/unprocessed candidates remain retryable. The merged history participates in the same backup/replacement/rollback boundary as the pages and JSON snapshots. A caught failed publication restores prior seen state.

Missing history starts as `{}`; unreadable, malformed or non-object history is never overwritten by the commit path. Existing direct `mark_papers_seen()` and `filter_new_papers()` interfaces remain available, but the production pipeline does not use their eager mutation path. Canonical identifiers, advanced retry-state modeling and transactional behavior for independent callers of those legacy helpers remain deferred.

## CLI and GitHub Actions policy

| CLI exit | Meaning |
| --- | --- |
| 0 | A publication completed; partial-source or extractive modes remain visible in metadata |
| 1 | Complete retrieval outage, required-runtime failure, fatal processing exception, or publication/recovery failure |
| 2 | Legitimate no-publication result: no eligible/new papers or no featured evidence; distinct from an outage |

`main()` returns this code and the script entry point uses `SystemExit(main())`; the installed console entry point also propagates the return code. A fatal exception emits a structured event including exception type and whether rollback recovery is required. A no-publication run leaves prior publication/state intact. CI treats both nonzero codes as a reason not to upload/deploy old content.

The existing GitHub Pages artifact deployment remains. The workflow:

- Uses Python 3.11 and installs the project's pinned direct dependencies/dev extra from `pyproject.toml`, with the existing PyTorch CPU index.
- Prepares MiniLM explicitly and requires it during refresh (`DIGEST_REQUIRE_EMBEDDINGS=true`); runtime metadata names `minilm` or `hashed_fallback`. The default local fallback algorithm is unchanged.
- Intentionally permits extractive fallback on CI. Ollama is not provisioned and `OLLAMA_HOST=http://127.0.0.1:1` prevents contacting a remote inference service. Summary generation modes are retained in JSON/HTML and counted in the manifest. The existing narrative fallback is unchanged and remains a separate scientific-honesty issue.
- Removes `continue-on-error`; tests, evaluation, refresh and current-run manifest validation must succeed before artifact upload. The expected ID combines GitHub run ID and attempt.
- Deploys only after the build job succeeds. Global permissions are contents-read; build additionally has pages-read for Pages configuration; only deploy has pages-write/id-token-write. No repository write permission or automated Git commit step is introduced.

Generated publication history/state is still not persisted back to Git by scheduled runs; durable scheduled history is a separate milestone. The code commit for this PR contains no generated production data. Model revisions and transitive dependency lock unification are not addressed here.

## Validation evidence

Fault injection covers temporary writes/flushes, successive replacements, restoration of previous content and seen history, retry after rollback, and retained backups/lock after rollback failure. Subprocess tests check actual CLI exit codes. Workflow YAML parses with PyYAML and its deployment gates are covered by a regression test; hosted GitHub Actions execution has not been exercised locally.

The existing unmodified offline audit probe was replayed with a controlled retrieval reference time of `2026-08-29T23:59:59Z`, blocked network/inference and temporary output directories. It fetched 12 eligible snapshot records, filtered to 9, and published 2 featured summaries plus 2 brief references. All 9 manifest artifact hashes validated; seen history contained exactly those 4 published URLs. Generation counts were `extractive_fallback: 2` and `not_generated: 2`.
